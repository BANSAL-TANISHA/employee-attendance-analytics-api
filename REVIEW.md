# Starter code review

The original starter was inspected against `openapi.yaml` and `DATA_MODEL.md`. The following concrete defects were found and addressed in `app/main.py`:


| # | Where | What is wrong / risk | How to notice it | Required correction |
|---|---|---|---|---|
| 1 | `department_summary()` | The contract says analytics endpoints must be MongoDB aggregation pipelines. This implementation aggregates attendance logs in MongoDB, but performs cross-collection joining/department roll-up and final averaging in Python. | Inspect the endpoint: it materializes employees/log groups into dictionaries and loops through them to produce department totals. | Move the employee-to-log join, zero-log headcount handling, grouping and average-over-records into one MongoDB aggregation pipeline. |
| 2 | `department_trend()` | The daily gap-fill, headcount calculation and 7-day moving average are performed in Python loops, not in MongoDB as required. | Inspect `daily_rows`, the `while d <= d_to` loop and the later `for i, row in enumerate(daily_rows)` loop. | Implement date generation/gap filling, daily grouped values, joined-date headcount and the rolling average in MongoDB. Keep the 92-day guard. |
| 3 | `explain_endpoint()` — all analytics branches | The endpoint explains simplified `$match` pipelines, not the actual query/pipeline used by the corresponding endpoint. It omits important stages such as grouping, lookup, window ranking, filters and pagination where applicable. | Compare each branch with its real endpoint. The department-trend explain only matches date range and does not use the selected department's employee codes. | Share pipeline/query builders between the real endpoint and explain endpoint; run `explain` with `executionStats` on the same pipeline and endpoint parameters. |
| 4 | `explain_endpoint()` — `attendance_list` | The explain branch does not validate `status` against the contract's allowed values or validate `date_from`/`date_to` in the same way as the real endpoint. Its parameter naming also differs from the actual endpoint (`date_from`/`date_to` versus `from`/`to` aliases where applicable). | Send invalid status/date filters to the explain route and compare behaviour with `/attendance`. | Match the real endpoint's parameter names, validation and query construction exactly. |
| 5 | `employee_monthly()` | `attendance_pct` is rounded to 2 decimal places, but R8 requires rates to be rounded half-up to 4 decimal places. | Use a ratio whose percentage has more than two meaningful decimal places and compare the response. | Use `_round_half_up(..., 4)` for `attendance_pct`. |
| 6 | `EmployeeIn.validate_joined_on()` | `date.fromisoformat()` accepts some ISO forms beyond the exact `YYYY-MM-DD` contract on supported Python versions; the original input is returned unchanged. | Try a non-canonical ISO date string and see whether it passes validation. | Require an exact `YYYY-MM-DD` pattern and round-trip/parse validation. Apply the same strictness to trend `from` and `to`. |
| 7 | `department_trend()` date validation | The code parses with `date.fromisoformat()` but does not enforce the exact input format. | Submit a valid ISO date in an alternate accepted representation and check whether it is accepted. | Validate exact `YYYY-MM-DD`, then parse; retain the reversed-range and 92-day checks. |
| 8 | `compute_late_minutes()` | Correctness depends on the supplied `attendance_date` representing the shift-start date. This helper handles the ordinary grace-period threshold, but must be tested with overnight shifts and early-morning punches against R1/R2 together. | For a 22:00–06:00 shift, test a 05:00 punch assigned to the previous day's shift and compare late minutes with the previous day's 22:00 start. | Keep the attendance-day/shift-start-date invariant explicit and test the overnight boundary. |
| 9 | `compute_overtime()` | Overtime logic chooses the next day's shift end when punch-out is before the same-day shift end. This is plausible for overnight shifts but needs tests for early punch-outs, exact 30-minute threshold and date assignment together. | Test an overnight shift punch-out before, exactly at, and after the next-day shift end. | Keep only if boundary tests prove R3 for overnight shifts; otherwise derive the shift-end instant explicitly from shift type and attendance date. |
| 10 | `create_indexes()` | Several indexes overlap: `(emp_code, date)` unique and `(emp_code, date DESC)`; `(date DESC, emp_code)` and `(date ASC, emp_code)`. Redundant indexes consume storage and add write cost. | Use `getIndexes()` and compare key patterns; measure explain plans for each real endpoint. | Retain only indexes justified by actual query plans. Keep the unique `(emp_code, date)` constraint because it enforces one record per employee/day. |
| 11 | `list_employees()` / `list_attendance()` | Pagination and filters must be verified against R10 and the exact OpenAPI response contract; passing current tests alone does not prove all filter combinations and `total` semantics. | Test each filter individually and in combination, page 1/page 2, maximum page size 100, and no-match results. | Ensure `total` is computed from the full filtered query before pagination and ordering exactly matches the contract. |
| 12 | `regularize()` | The compare-and-update uses a history-array-size predicate, which is a useful optimistic concurrency guard, but simultaneous updates can return 409 and require a retry. Confirm missing history is treated as `[]` and that audit entries contain only changed fields. | Seed a record with no `history`, submit a correction, and run simultaneous corrections with different reasons. | Preserve atomic update + `$push`; normalize missing history logically with `$ifNull`; test no lost audit entries and correct 409/retry behaviour. |
| 13 | `punch_in()` / `punch_out()` | Concurrency safety and HTTP status mapping rely on unique indexes and atomic conditional updates, not a pre-check alone. | Send simultaneous identical punch-ins and simultaneous punch-outs; assert exactly one 201 for punch-ins and exactly one 200 for punch-outs, with other requests returning the specified conflict response. | Keep database-enforced uniqueness for punch-in and a conditional atomic update for punch-out; map duplicate-key/already-closed cases to 409. |
| 14 | `_dt_to_ms()` / `_ms_to_dt()` and timestamp models | The contract requires epoch milliseconds to be integers, rejects seconds, floats, strings and out-of-range values, and truncates instants to whole seconds before calculations/storage/return. The model validators should be checked for Pydantic coercion behaviour before their validators run. | Send seconds, a float, a numeric string, a boolean and lower/upper out-of-range values to every timestamp field. | Use strict integer validation (while rejecting bool), validate bounds, and truncate before all calculations and persistence. |
| 15 | `department_summary()` average | Average work hours must be the average over qualifying records, not an average of per-employee averages. The current `wh_sum`/`wh_count` aggregation logic appears designed for record-level averaging, but must be tested for null/zero hours and non-present statuses. | Construct employees with unequal numbers of completed records, open records, absent/leave records and zero work hours. | Preserve record-level sum/count semantics and add expected-result tests. |
| 16 | `late_leaderboard()` | `$rank` is the right approach for skipped ranks (1, 2, 2, 4), but the `$rank` sort key must contain only total late minutes; the tie-break sort belongs after ranking. Verify `limit` is applied after rank so ties at the cutoff are all included. | Create totals 100, 80, 80, 60 with `limit=3`; expected ranks are 1, 2, 2, 4 and the first three rows include both employees tied at rank 2. | Keep `$rank`, apply rank cutoff after ranking, and sort tied output by `emp_code`. |
| 17 | Startup/configuration | The contract requires environment variables to override `.env`, indexes to be created idempotently at startup, and `/health` to report MongoDB readiness. | Start with externally supplied `MONGO_URI`/`MONGO_DB`, inspect indexes, and stop MongoDB to test readiness. | Keep configuration environment-first and verify startup/index creation/health against the target MongoDB version. |

## Reviewed and considered sound (subject to tests)

- A unique index on `employees.emp_code` is appropriate for the customer-owned employee identifier.
- A unique compound index on `attendance_logs (emp_code, date)` is necessary to enforce one record per employee/day and protect concurrent punch-ins.
- `_round_half_up()` uses `Decimal` and `ROUND_HALF_UP`, which matches the required rounding method when supplied the correct number of decimal places.
- The leaderboard uses `$rank`, which is the right ranking concept for skipped ranks; applying the cutoff after ranking is essential.
- Department headcount must include employees who joined by the period end even when they have no attendance records.
- `history` is an audit trail for manual corrections only; punch-in and punch-out must not append entries.
